## 1. What the project asks us to do

Take a small instruction-tuned model, **Qwen2.5-3B-Instruct**, measure how well it solves math and science problems,
then **supervised fine-tune (SFT)** it on 15,000 long chain-of-thought solutions drawn from a 100K subset of NVIDIA's
**AceReason-1.1-SFT** dataset, and measure again. The random 15K subset is the baseline. The real research question is
Section 7 of the README: *can a smarter way of choosing the 15K examples beat random selection?* We submit a GitHub repo,
the fine-tuned model and both datasets on Hugging Face, and a report. The top 5 teams on the class leaderboard get +10 points.

## 2. Core concepts you need

### 2.1 Supervised fine-tuning (SFT)
SFT continues training a pretrained model on (prompt, response) pairs with the ordinary next-token cross-entropy loss,
computed only on the response tokens. Here the responses are long "thinking" solutions, so SFT teaches the model to
*imitate* step-by-step reasoning, self-verification, and the `\boxed{}` answer format. No reward model and no RL are
involved. The model has 3B parameters and we do **full fine-tuning** (all weights update), not LoRA.

### 2.2 Long chain-of-thought (CoT) data
AceReason-1.1-SFT responses were generated by DeepSeek-R1 for prompts from OpenMathReasoning, OpenCodeReasoning and
NuminaMath-CoT. Outputs range from about 450 to 86,500 characters, roughly 100 to 20,000+ tokens. Consequences:
- Training sequences are long. The suggested `cutoff_len: 16384` truncates anything longer.
- After SFT the model will **answer much longer** at inference. That is why evaluation allows 32,768 output tokens and
  why evaluating the fine-tuned model takes far longer than evaluating the baseline.

### 2.3 Why these hyperparameters
| Setting | Value | Reason |
|---------|-------|--------|
| learning rate | 5e-6 | Full FT of a 3B model with few samples; small LR avoids erasing pretrained knowledge |
| per-device batch 1, grad-accum 8 | effective batch 8 | Long sequences do not fit larger micro-batches in memory |
| epochs | 3 | Common for small SFT sets; LIMO used up to 15 epochs on ~800 samples |
| scheduler | cosine, warmup 0 | Standard LLaMA-Factory recipe |
| bf16 | true | Halves memory, numerically safe on A100/H200 |
| flash_attn | fa2 | FlashAttention-2 makes 16K-token sequences feasible in memory and time |
| deepspeed | ZeRO-3 (+ optional CPU offload) | See 2.5 |

With 15,000 samples and an effective batch of 8, one epoch is about 1,875 optimizer steps, three epochs about 5,625.
Note: with multiple GPUs the effective batch becomes `GPUs x 1 x 8`. Lower `gradient_accumulation_steps` to keep the
effective batch near 8 to 16, or expect fewer steps per epoch.

### 2.4 LLaMA-Factory
A training wrapper around Hugging Face Transformers and TRL. You give it a YAML config and a dataset entry in
`data/dataset_info.json`, then run `FORCE_TORCHRUN=1 llamafactory-cli train config.yaml`. The data format is the Alpaca
style: `instruction`, `input`, `output`, `system`. The `template: qwen` line applies Qwen's chat template so the
trained model still answers correctly through the same chat template at eval time. The checkpoint folder must contain
the tokenizer and chat template files, otherwise the eval scripts produce bad scores without an obvious error.

### 2.5 DeepSpeed ZeRO and memory arithmetic
Full fine-tuning with AdamW in mixed precision needs about **16 bytes per parameter** (bf16 weights, fp32 master
weights, two fp32 optimizer moments, gradients). For 3B parameters that is about 48 GB *before* activations. At
16K-token sequences the activations are large even with gradient checkpointing, so:
- **1 x A100-80GB**: only fits with `ds_z3_offload_config.json` (optimizer and parameters offloaded to CPU RAM). It
  works but is slow because every step moves tensors over PCIe.
- **4 to 8 x A100-80GB on one node**: use `ds_z3_config.json` (no offload). ZeRO-3 shards weights, grads and optimizer
  states across GPUs, so each GPU holds about 6 to 12 GB of state and the rest is activations. Much faster. This is the
  recommended setup; the ARC A100 nodes have 8 GPUs each.

ZeRO stage summary: stage 1 shards optimizer states, stage 2 also shards gradients, stage 3 also shards parameters.

### 2.6 FlashAttention-2
An exact attention kernel that avoids materializing the full L x L attention matrix. Memory drops from quadratic to
linear in sequence length and it is 2 to 4 times faster. Required for 16K sequences. Install with
`pip install flash-attn --no-build-isolation`. The compile can take 20 to 60 minutes on a login node; if it fails, look
for a prebuilt wheel matching the torch and CUDA 12.6 versions.

### 2.7 vLLM and the evaluation harness
vLLM is a high-throughput inference engine using paged KV-cache memory and continuous batching. The `eval/` folder:
1. Generates 8 samples per question with temperature 0.6, top-p 0.95, max 32,768 tokens, seed 0, and the system prompt
   `"Please reason step by step, and put your final answer within \boxed{}."`
2. Extracts the last `\boxed{...}` block.
3. Grades with a SymPy/latex2sympy rule-based checker (exact match, numeric tolerance, or symbolic equivalence).
4. Writes `log_<benchmark>.txt` and per-sample JSONL under `OUTPUT_DIR/<model>/<benchmark>/`. Existing result files are
   skipped, so a timed-out `eval.sh` can simply be resubmitted and it resumes.

Env-var overrides: `MODEL`, `OUTPUT_DIR`, `CONDA_ENV`, `GPU_MEM_UTIL` (default 0.96). Example:
`MODEL=/path/to/ckpt OUTPUT_DIR=./outputs_ft sbatch eval.sh`.

### 2.8 Metrics: pass@1 vs pass@8
- **pass@1** = mean per-sample accuracy over the 8 samples. Printed as `Pass@1`.
- **pass@8** (`Acc` in the logs) = a problem counts as solved if *any* of the 8 samples is correct. Always at least pass@1.
- The **leaderboard average uses pass@8** over AIME25, CN_MATH_24, KAOYAN, AMC, MINERVA, OLYMPIADBENCH and GPQA.
  AIME24 and MATH-500 are reported but excluded from the average. AIME25 is on the leaderboard but is **not** in
  `eval/data`; the instructors evaluate it themselves.

### 2.10 Fall 2025 reference numbers (pass@8 average)
- Baseline Qwen2.5-3B-Instruct: **0.446**
- Random 15K SFT: **0.451 to 0.492**
- Best team: **0.525**

Takeaways: random SFT gives a few points; the best advanced strategies gave roughly +3 points over random. Several teams
*underperformed* the baseline (as low as 0.317), usually from training bugs (wrong template, truncation, bad LR), not
from data choice. A clean, non-broken run matters more than cleverness. GPQA swings wildly (0.53 to 0.81 across teams),
so watch it when comparing.

## 3. The referenced papers and what each contributes

| Paper | arXiv | Key idea relevant to us |
|-------|-------|-------------------------|
| **AceReason-Nemotron 1.1** (Liu et al., NVIDIA, 2025) | 2506.13284 | Source of our dataset. Scaling the *number of distinct prompts* helps SFT more than more responses per prompt. Stronger SFT models stay stronger after RL. Supports a **diversity / coverage** argument. |
| **OpenThoughts** (Guha et al., 2025) | 2506.04178 | 1,000+ controlled ablations of the SFT data pipeline. Findings: filter questions by **difficulty with an LLM judge**, prefer *longer* high-quality teacher responses, question diversity and source mixing matter, and verifying answer correctness was *not* essential. The best public recipe for reasoning SFT data. |
| **SimpleRL-Zoo** (Zeng et al., 2025) | 2503.18892 | Zero-RL across 10 base models. Shows **query difficulty must match the model's ability** (too hard gives no learning signal) and that longer responses do not automatically mean better reasoning. Motivates a *model-aware* difficulty filter using Qwen-3B's own pass rate, not solution length alone. |
| **LIMO** (Ye et al., GAIR, 2025) | 2502.03387 | 817 carefully chosen examples beat 100K-sample SFT on a 32B model. "Less is more": quality of the reasoning chain (elaboration, self-verification, exploration) and problem difficulty dominate quantity. Caveat: a 3B model has far less latent knowledge than 32B, so extreme minimalism may not transfer. |
| **LIMOPro** (GAIR, 2025) | github.com/GAIR-NLP/LIMOPro | **PIR: Perplexity-based Importance Refinement.** Segment each reasoning chain into functional steps (progressive reasoning, verification, multi-method validation, error correction), score each step by how much removing it raises the answer's perplexity, prune low-importance steps. Result: shorter responses *and* higher accuracy (+4 to +5 points on AIME for 32B). This edits the *responses*, not just which samples are chosen. |

Reading order if time is short: OpenThoughts (practical recipe), then LIMO (why selection works), then LIMOPro (a concrete pruning tool).

## 4. Data selection strategies: options and cost

| Strategy | How | GPU cost | Risk |
|----------|-----|----------|------|
| **Random** (required baseline) | sample 15K of 100K with a fixed seed | none | none |
| **Length / complexity proxy** | tokenize outputs, keep the middle-to-upper length band (about 2K to 12K tokens), drop anything above `cutoff_len` | CPU minutes | Weak proxy; may keep verbose junk |
| **Model-aware difficulty** | run Qwen-3B with vLLM on candidate prompts (2 to 4 samples, max 4K tokens), keep prompts solved 0 to 50 percent of the time | 100K prompts x 4 samples is about 25 to 40 A100-hours, so **score a 30 to 40K pool instead** (about 8 to 12 A100-hours) | Needs an answer key; check whether `extra_info` carries one |
| **Diversity (embeddings + K-Means)** | `sentence-transformers` on instructions, K-Means with k about 50 to 200, equal samples per cluster | under 1 GPU-hour | Gains were modest in Fall 2025 |
| **Hybrid (recommended)** | diversity clusters x difficulty band x length band, plus a domain mix (math vs code) matching the benchmarks | about 10 A100-hours | Must document every filter for the report |
| **LIMOPro PIR pruning** | apply PIR to the chosen 15K to shorten responses | several A100-hours of perplexity scoring | Pipeline was built for 32B; adaptation effort |

Practical note: the benchmarks are all math and science. A sizable share of AceReason is code. Filtering out code samples
is a cheap, defensible first move. Also drop samples whose output exceeds `cutoff_len`, so the model never trains on a
solution that was cut off before its final answer.

## 6. Common pitfalls

1. **Tokenizer or chat template missing from the checkpoint.** The model never writes `\boxed{}` and scores near zero.
2. **SLURM `--time` too short.** The README template says 1 hour. Use 12 to 24 h for training and 12 h or more for eval.
3. **Truncated training responses.** With `cutoff_len: 16384`, any solution longer than 16K tokens loses its final answer.
   Filter those samples out, or raise the cutoff if memory allows.
4. **GPQA is gated.** Request access on Hugging Face and run `huggingface-cli login` before evaluation.
5. **latex2sympy2 version pin.** Install with `--no-deps` exactly as the README says or omegaconf breaks.
6. **Noisy small benchmarks.** AIME (30) and CN_MATH (30) move by 0.033 per problem. Judge improvements on the average
   and on the large sets (olympiadbench, minerva, kaoyan).
7. **Leaderboard counts only the best model per team.** Submit the random model early as insurance.
8. **Keep the eval JSONL outputs.** Instructors may request them and they are the raw material for the report's analysis.
9. **Multi-GPU changes the effective batch.** Adjust `gradient_accumulation_steps` when moving from 1 to 4 or 8 GPUs.
